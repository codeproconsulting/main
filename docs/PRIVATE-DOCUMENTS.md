# Private client documents

From a CRM lead, open **Documents**. Select the category, attach a PDF, JPEG, PNG or WebP and optionally enter the expiry day. The limit is 20,000,000 bytes per file. The expiry day is inclusive in Pakistan time. Reviewers can record an outcome and notes. The checklist shows whether each category has a scanned, accepted, unexpired document. The categories are a guide and do not prescribe requirements for a destination or case. Expired files remain available for authorized staff to inspect. An older record without a scan marker requires re-upload from a trusted source before download or review. It stays visible as **Scan required**.

The app checks the extension, MIME type, signature and size, then sends the bytes to a local ClamAV daemon. A confirmed clean verdict is required before Appwrite receives any bytes. Detected malware, incomplete results, outages and scan timeouts fail closed. Downloads open only after a CRM role check, a current lead access check and an audit intent. The response is an attachment with private no-store caching. An already started download can finish if ownership changes during streaming.

## Release checks on the target host

1. Install or expose the trusted ClamAV daemon through a Unix socket accessible to the CRM service user. Restrict filesystem access to that socket and run regular signature updates. Set `CRM_CLAMD_SOCKET` in the CRM service environment. Configure ClamAV stream and scan limits above 20,000,000 bytes and enable alerts for files exceeding internal scan limits or encrypted content if those files cannot be inspected. Confirm the running configuration with the actual daemon.
2. Run `node scripts/setup-appwrite.mjs --only=documents` to preview the additive attributes. With the scoped setup key, run the same command with `--apply` and wait for the attributes to become available. The fields are `scannedAt`, `reviewVersion`, and `reviewNotes`. Leave the scan marker blank for legacy records. Run `node scripts/setup-storage.mjs --only=documents` to check the private bucket and its settings. The current bucket permits up to 20 MiB. The app enforces the smaller 20 MB limit and sends files in Appwrite chunks. Verify the effective Appwrite encryption and scan settings on the installed version as part of release acceptance.
3. In an isolated CRM/Appwrite environment, confirm clean upload and byte-identical download of a synthetic small file and a synthetic file close to the limit. Confirm anonymous bucket access and out-of-scope counselor access fail. Exercise a safe antivirus test signature inside a supported fixture using the actual ClamAV daemon. Check that detection and scanner downtime leave no new file or metadata. Use the production-equivalent proxy and service account for these checks. Remove disposable records and files afterward.
4. Confirm list, checklist, review and download as assigned counselor, former assignee, manager and content staff before accepting the feature on the VPS.

## Recover an interrupted upload

Use the lead activity history to identify **Document upload requested** with pending state. Details contain generated document/file IDs. Keep IDs and findings in the restricted operator workspace and never copy file names, notes or content into deployment logs.

- Compare the document record with the file in the private document bucket. If the metadata matches the lead and file and the file is complete, keep both and reconcile the activity as completed. If metadata exists and the file is missing or incomplete, keep the record for investigation and collect a scanned replacement.
- If metadata is absent and the file exists, leave it private until you can establish that the original request and any retries have stopped. Stop or quiesce the dashboard, allow in-flight writes to finish, and repeat the metadata/reference checks. Remove only the exact unreferenced file tied to the pending intent. If the checks disagree or the state is ambiguous, preserve it for investigation. If neither exists, record the attempt as rolled back. Do not retry the upload while the previous outcome is uncertain.
- If a review shows a pending intent, compare its version and intended status to the current record before retrying or reconciling. Use the existing abandoned lock procedure if the per-lead lock remains held after the original process stops.

The app compensates automatically only after a definite metadata rejection and a confirmed missing record. A timeout, failed cleanup or ambiguous storage response retains the pending intent for an administrator.
